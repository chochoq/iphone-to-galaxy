# 공개 저장소 설계 인덱스

## 0. 목적과 출발점

이 저장소는 앱 세 개를 한 폴더에 모으는 일이 아니다. iPhone 3GS부터 iPhone을 사용해 온 한
사용자가 iPhone 14 Pro / iOS 26.6.1에서 익숙해진 동작을 Galaxy Z Fold8 / Android 17 /
One UI 9.0으로 옮기며 생긴 문제, 실패한 우회법, 최종 선택과 되돌리는 법을 공개하는 작업이다.

마지막 iPhone 정보는 “호환 기기”가 아니라 경험의 기준이다. Galaxy 정보는 유일하게 직접 시험한
범위다. 특히 Fold8의 화면 크기와 시스템 UI를 다른 Galaxy에 일반화하지 않는다.

## 2. 사용자 시나리오와 반복 검증

### S-001 — 같은 불편을 검색해 들어온 iPhone 전환 사용자

사용자는 앱 이름보다 “상태 표시줄을 눌러 맨 위로 가고 싶다” 같은 행동으로 검색한다. 첫 화면에서
자기 iPhone 경험과 시험 Galaxy가 같은지 확인하고, 가장 낮은 해결 수준부터 읽으며, 권한과
원상복구를 이해한 뒤 적용한다.

첫 검토에서는 앱별 구조가 구현자에게는 자연스럽지만 문제를 검색한 사람에게는 입구가 되지
않는다고 판단했다. 두 번째 검토에서 README에 문제 지도를 두고 앱은 해결책으로 연결했다. 세 번째
검토에서 “직접 앱”과 “검증 완료”가 같은 의미로 오해될 수 있어 해결 수준과 검증 상태를 분리했다.

### S-002 — 다른 Galaxy에서 재현하려는 기여자

기여자는 모델·Android·One UI뿐 아니라 Fold 커버/메인 화면, 글자 크기와 내비게이션 방식을
기록한다. 성공도 `지원`으로 일반화하지 않고 날짜가 있는 `직접 검증` 한 행으로 추가한다. 실패는
삭제하지 않고 어떤 화면과 앱에서 왜 실패했는지 남긴다.

### S-003 — 권한이 불안한 비개발자

사용자는 접근성·캘린더·방해 금지·Bluetooth·다른 앱 위 표시 권한의 범위를 먼저 보고, 광고와
서버 전송 여부를 확인하며, 적용하지 않기로 했을 때 되돌리는 경로까지 알아야 한다. APK만 먼저
배포하면 이 판단 순서가 뒤집히므로 초기 공개는 source-first로 한다.

### S-004 — 미래의 유지관리자

유지관리자는 깔끔한 최종 결론만 보는 것이 아니라 가설, 반례, 설계 수정, 예상 결과, 실기기 시험을
따라갈 수 있어야 한다. 앱 내부의 상세 설계·태스크·결과 문서를 보존하고 우산 저장소의 문제 문서가
그 이력을 가리키게 한다.

## 3. 선택 원칙과 의존성 순서

해결 순서는 Galaxy 설정 → Samsung/Good Lock → 신뢰할 수 있는 기존 앱 → ADB·자동화 → 직접
앱이다. 개발 순서는 문서에 보이는 순서와 다르다. 가장 많은 하위 작업이 의존하는 공개 경계,
권한·데이터 계약, 재현 가능한 빌드, 상태 모델을 먼저 고정하고 UI와 소개 문서를 그 위에 얹는다.

이번 이관에서 실제로 절대 SDK 경로와 개인 서명 키 방식이 세 앱의 공개 빌드를 막는 공통 의존성으로
발견됐다. 따라서 문제 설명보다 공통 SDK 탐색·debug signing 경계를 먼저 만들었다. AirPods의
디자인 자산은 런타임에 필요한 CC BY 파생 렌더와 notice만 포함하고, Apple 공식 캡처·비교 영상과
실패한 대용량 산출물은 제외한다.

구현 뒤 공개 staging 자체로 세 앱을 다시 빌드했다. 공통 helper는 예상대로 사용자 경로 없이 SDK를
찾았고, 세 APK 서명 검증, AirPods 262,649 core assertions와 permission policy를 통과했다. 이 결과로
공통 빌드 구조를 유지한다. Holiday Sleep의 deprecated API와 AirPods receiver의 deprecated API
compile note는 실패가 아니지만 차기 Android API 조사 항목으로 남긴다.

## 4. 공개 게이트

1. 추적 파일에 개인 위치·기기 식별자·개인 AirPods 이름·절대 사용자 경로가 없어야 한다.
2. keystore, APK, 로그, 화면 녹화, 외부 앱 APK와 공식 제품 이미지가 없어야 한다.
3. 세 앱이 깨끗한 build 디렉터리에서 빌드되고 AirPods core/policy 검사가 통과해야 한다.
4. 각 문제에 권한, 데이터, 한계, 원상복구와 검증 환경이 있어야 한다.
5. 프로젝트·문서 라이선스는 소유자가 확정해야 한다.
6. 원격 저장소 URL, 보안 신고 경로와 공개 시점을 확인한 뒤에만 push한다.
7. 새 직접 앱 전에는 GitHub·F-Droid·Play Store의 기존 해법을 확인하고, 더 나은 대안이 있으면 먼저
   안내한다. 기능의 중복과 설계 차이를 최초성 주장으로 바꾸지 않는다.

## 5. 변경 규칙

새 관찰은 결과 문서에 사실로 기록한다. 기존 가정을 깨면 문제 문서와 설계 결정을 먼저 갱신하고,
태스크의 완료 조건을 바꾼 뒤 구현한다. 구현 전에 예상 결과와 중단 기준을 쓰고, 시험 뒤 실제 차이를
분석한다. 실패를 지워 README를 매끈하게 만들지 않는다.

## 6. 글쓰기 원칙

처음 작성한 공개 문서는 사실관계는 정확했지만 영어 명사를 연달아 쓰고 추상적인 원칙부터
설명했습니다. 사용자가 겪은 불편이 뒤로 밀려서, 내용보다 프로젝트 소개문 같은 인상이 강했습니다.

`snflkd/fluent-korean`과 `epoko77-ai/im-not-ai`의 공개 문서와 실제 지침을 읽고 다음 순서로
고쳤습니다.

1. README와 문제 문서는 사용자가 겪은 장면에서 시작합니다.
2. 이미 쓸 수 있는 설정과 앱을 먼저 소개한 뒤 직접 만든 이유를 설명합니다.
3. 한국어로 풀어 쓸 수 있는 영어 명사 나열을 줄이고 완성된 문장으로 씁니다.
4. 기능이 처음이거나 모든 기기에서 잘된다는 인상을 주지 않습니다.
5. 확인한 사실, 그 사실에서 내린 판단과 아직 시험하지 않은 범위를 나눠 적습니다.
6. 실패 기록과 기술 용어가 필요한 설계 문서는 짧게 꾸미기보다 정확성을 우선합니다.

첫 검토에서는 README에 개인 경험을 앞세우고 문제·앱·설정 안내의 영어 혼용을 줄였습니다. 두 번째
검토에서는 기존 프로젝트 조사와 라이선스 문서도 같은 목소리로 고쳤습니다. 세 번째 검토에서는
공개 문서의 링크와 금지 파일 검사를 다시 실행하고, im-not-ai의 정량 측정으로 주요 문서가 모두
낮은 위험도로 나오는지 확인했습니다. 이 측정은 자연스러운 글을 증명하는 점수가 아니라 기계적인
표현이 다시 늘었는지 살피는 보조 자료로만 사용합니다.
