# 공개 이관 태스크와 판단 이력

## 1. 공개 경계를 먼저 고정한다

### 1.1 개인 room과 공개 저장소를 물리적으로 분리한다

#### 1.1.1 새 `iphone-to-galaxy/` staging만 공개 후보로 삼는다 — 완료

기존 room에는 연속성 메모리, 기기 상태, 설치 APK, keystore와 시험 영상이 함께 있다. `.gitignore`
만 믿고 room 자체를 저장소로 만들면 미래의 강제 추가나 규칙 변경으로 유출될 수 있다. 별도 디렉터리를
만들고 허용한 파일만 복사했다. 공개 검사는 항상 이 디렉터리를 기준으로 한다.

#### 1.1.2 개인 식별 흔적과 배포 금지 바이너리를 검색한다 — 1차 완료

집·회사 위치, 개인 AirPods 이름, macOS 사용자 절대 경로, Bluetooth 주소, serial, 암호·서명 옵션을
검색했다. 앱 소스에는 위치·주소가 없었지만 AirPods 설계·결과 문서에 개인 제품명이, 기존 build
스크립트에는 절대 SDK 경로와 로컬 서명이 있었다. 제품명은 일반 시험명으로 바꾸고 빌드를 공통
도구로 교체했다. Git 추적 직전에 두 번째 검사를 실행한다.

두 번째 검사와 binary metadata 검사까지 통과했다. `chochoq`/`com.chocho`는 소유자가 공개 GitHub
nickname으로 유지한다고 2026-09-07 확인했으므로 금지 문자열로 분류하지 않는다. commit email은
GitHub noreply만 유지한다.

### 1.2 권리와 안전 경계를 고정한다

#### 1.2.1 제3자 코드와 이미지의 출처를 분리한다 — 완료

HiddenApiBypass 6.1은 Maven 원본 URL과 SHA-256을 빌드에 고정하고 binary는 추적하지 않는다.
AirPods turntable은 polyman CC BY 4.0 모델의 파생 렌더임을 소스와 APK notice 양쪽에 유지한다.
Apple 공식 비교 영상·캡처, MaterialPods 및 다른 앱의 APK·자산은 공개본에 복사하지 않았다.

#### 1.2.2 프로젝트 라이선스를 확정한다 — 완료

처음에는 코드 Apache-2.0, 문서 CC BY 4.0을 제안했습니다. 소유자는 다른 사람이 코드를 판매하는
것보다, 개선한 결과를 다시 공개하지 않아도 된다는 점을 더 불편하게 느꼈습니다.

상업 이용을 막는
조건은 일반적인 오픈소스가 아니며 호환성도 낮아지는 점을 함께 확인했습니다.

그 결과 코드에는 GPL-3.0-or-later, 직접 쓴 문서에는 CC BY-SA 4.0을 적용했습니다. 루트에는 GPL
전문을, `LICENSES/`에는 문서와 제3자 저작물의 전문과 파일별 범위를 넣었습니다.

AirPods 렌더의
CC BY 4.0과 HiddenApiBypass의 Apache-2.0은 프로젝트 라이선스로 덮지 않았습니다.

라이선스 결정은 공개 전환 허락이 아닙니다. 저장소는 비공개로 유지한 채 검사와 원격 백업만 먼저
마치고, 공개 전환은 별도 확인을 받습니다.

#### 1.2.3 저장소 설명과 APK 안의 라이선스가 같은지 검증한다 — 완료

루트 GPL 전문만 추가하면 GitHub 대표 라이선스는 분명해지지만 문서와 외부 렌더의 조건이 가려질
수 있습니다.

파일별 범위를 별도 문서에 적고, CC BY-SA 4.0·CC BY 4.0·Apache 2.0 전문을 함께
둡니다.

AirPods Glance는 HiddenApiBypass 코드와 CC BY 렌더를 실제 APK에 넣으므로 저장소 링크만으로
끝내지 않습니다. 두 전문과 저작자 고지를 Android raw resource에 포함하고, 루트의 전문과 APK용
복사본을 `cmp`로 비교한 뒤에만 빌드하도록 했습니다.

예상 결과는 GitHub가 루트의 GPL-3.0을 인식하고, 로컬 링크와 공개 파일 검사가 통과하며, 만들어진
APK에서 제3자 고지와 두 전문을 다시 꺼낼 수 있는 것입니다. 하나라도 다르면 라이선스 범위 문서나
빌드 구성을 먼저 고치고 공개 준비 완료로 표시하지 않습니다.

공식 원문 네 개의 SHA-256, Markdown 링크와 공개 파일 검사가 통과했습니다. 세 앱도 다시 빌드됐고,
AirPods APK에서 꺼낸 고지와 CC BY 4.0·Apache 2.0 전문이 저장소 파일과 정확히 일치했습니다.

비공개 원격에 올린 뒤 GitHub는 대표 라이선스를 GNU GPLv3로 인식했습니다. 원격 자동 검사도
공개 파일 검사, 세 앱 빌드, AirPods 핵심 검사와 APK 고지를 모두 통과했습니다.

## 2. 공통 의존성을 먼저 재구축한다

### 2.1 세 앱이 사용자 컴퓨터 경로 없이 빌드되게 한다

#### 2.1.1 SDK 탐색과 debug signing을 공통 도구로 옮긴다 — 완료

기존 세 스크립트는 한 Mac의 사용자별 Android SDK 절대 경로와 앱별 keystore에 묶여 있었다. 환경 변수,
macOS/Linux 기본 SDK 위치, Platform/Build Tools 존재를 확인하는 `tools/android-env.sh`를 만들었다.
생성되는 `.local/debug.jks`는 공개 배포 키가 아니고 Git에서 제외된다. 이 구조가 실패하면 개별 앱
UI를 고치기 전에 공통 도구부터 수정한다.

#### 2.1.2 깨끗한 상태에서 앱 세 개와 core/policy 검사를 실행한다 — 완료

Tap to Top, Holiday Sleep, AirPods Glance 순서는 제품 중요도가 아니라 빌드 복잡도 증가 순이다.
마지막 앱은 checksum dependency, 262,649 core assertions와 APK permission gate까지 확인한다.
산출물은 추적하지 않는다.

2026-09-07 공개 staging에서 세 debug APK가 생성·서명 검증됐다. AirPods dependency SHA-256,
262,649 assertions와 forbidden permission/manifest policy도 통과했다. 생성된 `build/`, `.local/`,
`deps/`는 모두 ignored 상태이며 Git index에는 들어가지 않았다.

## 3. 문제 중심 탐색 구조를 만든다

### 3.1 사용자가 앱 이름을 몰라도 입구를 찾게 한다

#### 3.1.0 직접 앱의 기존 공개 대안을 다시 조사한다 — 완료

공개 직전 “기능 하나씩 보면 이미 비슷한 GitHub가 많지 않겠느냐”는 소유자의 질문을 가설로 두고
repository search와 README·license를 확인했다. AirPods companion은 LibrePods, CAPod, OpenPods,
Podsify 등 성숙한 대안이 있었고, 같은 목적의 TapToTop 접근성 앱도 찾았다. 한국 공휴일 수면 연장과
문제 중심 전환 저장소의 명확한 대응물은 이번 검색에서 찾지 못했지만 부재로 확정하지 않는다.

이 결과로 AirPods Glance와 Tap to Top을 최초·범용 제품으로 소개하지 않고, 기존 대안과 다른 설계
trade-off를 가진 단일 기기 사례로 낮춰 표현했다. 새 직접 앱 전의 landscape 확인을 공개 gate에
추가했다.

#### 3.1.1 README 문제 지도와 여섯 문제 문서를 연결한다 — 완료

각 문서는 iPhone 경험, Galaxy 차이, 검토 단계, 선택, 권한·부작용, 되돌리기, 검증 범위와 미확정을
같은 순서로 쓴다. 설정의 메뉴명이 One UI 업데이트로 달라질 수 있으면 정확한 문자열을 꾸며내지
않고 목표 설정과 현재 검증 버전을 함께 쓴다.

#### 3.1.2 설정 레시피를 개인 위치 없이 일반화한다 — 완료, 세부 기기 재확인 표기

귀가·외출 루틴에는 실제 집/회사 주소를 넣지 않는다. 독자는 자기 장소나 신뢰 Wi-Fi를 선택해야
한다. 회의·수면·경보·제스처도 사용자의 안전 선택을 기본값처럼 강요하지 않는다.

#### 3.1.3 공개 문서에서 기계적인 설명투를 걷어낸다 — 완료

첫 문서는 공개할 사실을 빠뜨리지 않는 데 집중하면서 `해결 수준`, `검증 경계`, `source-first` 같은
추상어와 영어 명사가 앞에 나왔습니다. 내용은 맞았지만 아이폰에서 Galaxy로 옮긴 사람의 실제
경험이 잘 보이지 않았습니다.

fluent-korean에서는 생략된 문장 성분을 복원하고 조사와 어미를 갖춘 문장으로 쓰는 방법을
살폈습니다. im-not-ai에서는 기계적인 대구, 영어 명사 나열, 과한 표제와 최초성 주장을 줄이는
기준을 확인했습니다. 두 프로젝트의 문장을 복사하지 않고 우리 문서의 역할에 맞게 적용했습니다.

먼저 README를 개인 경험에서 시작하도록 다시 썼습니다. 그다음 문제 문서, 설정 방법, 앱 README,
호환성·보안·기여·라이선스와 기존 프로젝트 조사 문서를 같은 기준으로 고쳤습니다. 설계와 시험
기록은 과거 판단을 바꾸지 않도록 사실과 수치를 유지했습니다. 마지막으로 링크 검사, 금지 파일
검사와 주요 문서의 정량 문체 검사를 실행합니다.

첫 수정 뒤 사용자가 GitHub에서 실제로 읽을 때 필요한 줄바꿈도 넣어 달라고 요청했습니다. Markdown
소스의 단순한 줄 나눔은 GitHub에서 한 문단으로 이어지므로, 주제가 바뀌는 지점에는 빈 줄을 넣어
실제 화면에서도 문단이 나뉘게 했습니다. 표와 순서 목록은 항목 자체가 구분되므로 억지로 쪼개지
않았습니다.

#### 3.1.4 회의 녹음이 허용된다는 개인 환경의 가정을 분리한다 — 완료

처음 회의 모드를 만든 회사에서는 회의록을 위해 녹음을 권장했습니다. 사용자가 다른 회사에서는
그렇지 않을 수 있다고 지적하면서, 개인 환경의 관행이 공개 레시피의 전제가 되어 있음을
발견했습니다.

문제 문서에는 이 기능이 시작된 배경과 법률 자문이 아니라는 범위를 적었습니다. 설정 문서에는
회사 규정, 참석자 안내·동의, 고객사와 비밀유지계약, 개인정보, 저장·공유·보관·삭제를 확인하는
목록을 넣었습니다. 규정을 확인할 수 없는 경우에는 녹음 앱 열기를 빼고 나머지 회의 설정만 쓰도록
안내했습니다.

### 3.2 공개 후 처음 사용하는 사람의 진입 경로를 보완한다

#### 3.2.1 개발자 옵션부터 PC 승인·앱별 권한까지 따라갈 수 있게 적는다 — 문서 반영

사용자가 공개 후 받은 질문은 ‘어떤 앱인가’보다 ‘무엇을 설치하고 폰 권한을 어디까지 여는가’였습니다.
README에는 빌드 SDK만 있었으므로 설정만 할 사람, PC로 작업할 사람, 앱을 설치할 사람의 준비를
표로 구분하고 개발자 옵션·빌드번호 일곱 번·USB 디버깅·PC 승인 순서를 본문에 추가했습니다.

상세 안내에는 ADB 실행 위치, Windows 드라이버, 연결 상태별 확인, 세 앱의 실제 APK 경로와
앱별 권한을 적었습니다. 빌드 스크립트와 MainActivity·Manifest, Android 공식 개발자 옵션·실기기
연결 문서를 대조했습니다. 루팅이나 OEM 잠금 해제를 요구하지 않고, 작업 후 해제 방법도 포함했습니다.

#### 3.2.2 경로·권한·문서 링크를 대조하고 검증 한계를 남긴다 — 문서 검사 완료

APK 경로는 세 build.sh의 산출물과, 권한은 Manifest와 설정 화면을 여는 소스와 비교했습니다.
Markdown 상대 링크와 공개 파일 검사, `git diff --check`가 통과했습니다. 새 사용자 폰의 최초 연결·설치와 Windows 빌드는
수행하지 않았으므로 안내의 확인 범위에 미검증으로 적습니다. 이번 요청은 공개 README 보완이며,
room의 앱 기능 변경을 함께 내보내지 않습니다.

### 3.3 공개 안내에서 생략한 뜻을 복원한다

#### 3.3.1 ‘한 기기에서 확인’과 ‘실험용’이 독자에게 무엇을 뜻하는지 풀어 쓴다 — 반영

기존 README에는 다음과 같이 적었습니다.

> `한 기기에서 확인`과 `지원`은 다릅니다. 숨은 Android API나 기종별 동작에 기대는 기능에는
> `실험용`이라고 따로 표시합니다.

사용자는 이 문장의 뜻을 물으며 fluent-korean을 적용해 이해하기 쉽게 써 달라고 요청했습니다.
fluent-korean의 README와 `plugins/fluent-korean/output-styles/fluent-korean.md` 전문을 읽었습니다.
플러그인을 설치하지 않고, 생략한 문장 성분과 의미를 복원하는 글쓰기 지침을 이번 편집에 적용했습니다.

이전 문장은 용어들의 차이만 선언하고 실제 의미를 독자가 추측하게 했습니다. README에는 Fold8에
설치해 동작을 직접 확인했으며 다른 Galaxy에서는 아직 확인하지 않았다고 썼습니다. ‘실험용’은
에어팟 배터리 읽기가 기종이나 Android 업데이트에 따라 작동하지 않을 수 있다는 말로 설명했습니다.
새로운 호환성 시험을 했거나 기기 지원 범위를 넓혔다는 뜻은 아닙니다.

## 4. 결과를 예측하고 공개 게이트를 시험한다

### 4.1 예상 결과를 먼저 적는다

#### 4.1.1 저장소와 앱의 예상 상태를 기록한다 — 완료

예상은 세 앱의 로컬 debug APK 생성, AirPods core/policy 통과, 금지 문자열·binary 0건, Git 추적
후 ignored 산출물만 남는 것이다. 예상과 다른 항목은 지우지 않고 결과 문서에서 원인과 설계 반영을
연결한다.

예상과 실제는 일치했다. 139개·약 5 MiB의 공개 파일만 index에 올랐고, 허용한 runtime PNG/WebP
네 개 외에 APK·AAR·JAR·keystore·영상·로그는 추적되지 않았다. Markdown 상대 링크, shell 문법과
GitHub YAML도 별도로 검사했다.

### 4.2 원격 공개 직전 사람의 결정을 받는다

#### 4.2.1 저장소 소유권·URL·라이선스·최초 배포 범위를 확인한다 — 공개 시점 확인 대기

GitHub 계정과 저자 이름, source-first 범위, 코드와 문서의 라이선스까지 확인했습니다. 저장소를
비공개에서 공개로 바꾸는 일은 별도의 외부 상태 변경이므로 자동으로 진행하지 않습니다. 설치 APK
release도 다기기 검증과 배포 서명·업데이트 경로를 정한 뒤 따로 결정합니다.
