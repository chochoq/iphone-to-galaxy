# 001 — 제품 범위와 사용자 시나리오

## 1. 문제 정의

사용자가 원하는 것은 AirPods의 기능을 모두 Android에 복제하는 관리 앱이 아니다.
현재 불편은 AirPods를 켤 때마다 제3자 앱이 광고·평가·구매 같은 불필요한 표면을
함께 띄우고, 정작 자주 확인하는 배터리 정보는 조용하고 지속적인 자리에 남지 않는
것이다.

따라서 1차 제품의 질문은 다음과 같다.

> 사용자의 AirPods가 연결되어 있을 때, 광고나 계정 없이 좌·우·케이스 배터리를
> 믿을 수 있는 범위에서 보여 주고, 팝업을 놓친 뒤에도 홈 화면 위젯에서 바로
> 확인하게 할 수 있는가?

## 2. 사용자 시나리오

### S-001 — 이어폰을 꺼내 연결한다

1. 사용자가 AirPods를 착용한다.
2. Android가 이미 페어링된 AirPods와 오디오 연결을 맺는다.
3. 앱은 연결 이벤트를 받아 그 연결 세션에서만 BLE 배터리 신호를 관찰한다.
4. 첫 번째 신뢰 가능한 배터리 상태를 얻으면 일회성 알림을 보여 준다.
5. 알림에는 왼쪽, 오른쪽, 케이스가 서로 구분되어 보인다.
6. 값이 없는 구성요소는 0%가 아니라 `—`로 보인다.
7. 같은 연결 세션에서는 패킷이 반복되어도 팝업을 다시 띄우지 않는다.

성공 기준은 “무언가 떴다”가 아니라, 광고 없이 한 번만 나타나고 잘못된 값을
확정적으로 말하지 않는 것이다.

### S-002 — 팝업을 놓치고 홈 화면에서 확인한다

1. 사용자가 연결 알림을 닫았거나 보지 못했다.
2. 홈 화면 위젯을 본다.
3. 위젯은 좌·우·케이스 배터리와 충전 상태를 한 화면에 표시한다.
4. 마지막 관측이 오래되었으면 `방금`처럼 보이지 않고 갱신 시각을 표시한다.
5. 위젯의 새로고침을 누르면 연결 중인 경우 즉시 다시 관찰을 요청한다.

### S-003 — 한쪽 이어버드만 쓴다

1. 한쪽은 귀에 있고 다른 한쪽은 케이스에 있다.
2. 앱은 주 이어버드가 바뀌어도 좌우 값을 뒤집지 않는다.
3. 케이스 안의 이어버드에 충전 표시가 나오고, 귀에 있는 쪽에는 나오지 않는다.
4. 해당 시나리오가 실기기 좌우 해석의 최종 검증 기준이 된다.

### S-004 — 배터리가 부족하다

1. 좌·우 중 하나가 20% 이하이거나 케이스가 15% 이하로 처음 내려간다.
2. 앱은 연결 팝업과 분리된 배터리 부족 알림을 한 번 보낸다.
3. 같은 단계의 반복 패킷에는 알림을 반복하지 않는다.
4. 충전 또는 임계값 위 회복 뒤 다시 내려갈 때 새 세션으로 판단한다.

### S-005 — 연결이 끊긴다

1. 회의 모드가 Bluetooth를 끄거나 사용자가 AirPods를 케이스에 넣는다.
2. 앱은 스캔과 foreground service를 멈춘다.
3. 연결 중 알림은 사라진다.
4. 위젯은 마지막 값을 흐리게 유지하되 `연결 안 됨 · 마지막 확인 …`으로 표시한다.
5. 과거의 충전 비트를 현재 충전 중인 것처럼 표시하지 않는다.

### S-006 — 주변에 다른 AirPods가 있다

1. 회사나 대중교통에서 같은 모델의 AirPods 광고가 여러 개 수신된다.
2. 앱은 사용자의 페어링 기기 연결 여부를 먼저 확인한다.
3. 연결되지 않았으면 어떤 주변 AirPods도 위젯의 현재 값으로 채택하지 않는다.
4. 연결 중이어도 기기 주소가 일치하지 않는 후보는 진단 대상으로 남기고 자동 확정하지
   않는다.

### S-007 — 권한이 없거나 Bluetooth가 꺼져 있다

1. 위젯은 빈 배터리 숫자를 만들지 않는다.
2. `Bluetooth 권한 필요` 또는 `Bluetooth 꺼짐`처럼 사용자가 할 수 있는 다음 행동을
   알려 준다.
3. 위젯을 누르면 앱의 권한 안내 화면으로 이동한다.

### S-008 — 휴대폰이 재부팅된다

1. 위젯은 저장된 마지막 상태로 다시 렌더링된다.
2. 연결되지 않은 동안 상시 스캔 서비스를 자동으로 띄우지 않는다.
3. 이후 AirPods 연결 이벤트가 오면 정상 감시를 다시 시작한다.

### S-009 — 화면을 보는 중 AirPods가 연결된다

1. 휴대폰 화면이 켜지고 잠금이 풀린 상태에서 AirPods가 연결된다.
2. 앱은 정확한 첫 battery snapshot을 받은 뒤 화면 상단에 큰 연결 카드를 한 번 띄운다.
3. 카드는 AirPods 이름, 왼쪽·오른쪽·케이스 값과 충전을 한눈에 보여 준다.
4. 사용자가 카드를 누르면 앱을 열고, 닫기 버튼을 누르거나 6초가 지나면 사라진다.
5. 화면이 꺼짐·잠김 상태거나 특별 권한이 없으면 큰 카드를 억지로 띄우지 않고 기존 시스템
   알림과 위젯 갱신으로 대체한다. 방해 금지는 소리·진동을 만들지 않는 이 카드 자체를 막지 않는다.
6. 같은 연결에서 battery push가 반복돼도 카드가 다시 뜨지 않는다.

성공 기준은 전체 화면을 빼앗는 것이 아니라, MaterialPods에서 유용했던 즉시성만 가져오고
광고·평가·구매 버튼과 상시 overlay는 가져오지 않는 것이다.

## 3. 시나리오별 베스트 프랙티스

### BP-001 — 모르는 값을 솔직하게 표시한다

- BLE 공개 배터리는 10% 간격이다. `83%` 같은 허위 정밀도를 만들지 않는다.
- 미수신, 알 수 없음, 오래된 값을 모두 0%와 구분한다.
- 숫자와 함께 신선도와 연결 상태를 표시한다.

### BP-002 — 표면은 사건에 비례한다

- 연결 사건에는 팝업 한 번만 사용한다.
- 연결 중 지속 정보는 조용한 알림과 위젯이 담당한다.
- 연결 해제 뒤에는 대기 알림을 남기지 않는다.
- 낮은 배터리 알림은 임계값을 통과할 때만 보낸다.

### BP-003 — 주변 기기 프라이버시를 정확성 문제로 함께 다룬다

- Apple 제조사 패킷이라는 이유만으로 내 기기로 간주하지 않는다.
- 페어링된 기기와 실제 오디오 연결이 먼저 성립해야 한다.
- 주소 일치 여부, 모델, RSSI, 연결 시각을 후보 판단에 쓰되 원시 주소를 로그나 UI에
  노출하지 않는다.

### BP-004 — 위젯은 캐시 뷰이며 스캐너가 아니다

- `AppWidgetProvider` 자체가 장시간 BLE 스캔을 수행하지 않는다.
- 상태 저장소의 한 스냅샷을 빠르게 렌더링한다.
- 수신 서비스가 상태를 원자적으로 갱신한 뒤 모든 위젯을 다시 그린다.
- 새로고침은 서비스에 요청할 뿐 위젯 프로세스를 오래 붙잡지 않는다.

### BP-005 — Android 정책을 우회하지 않는다

- 연결 중 감시는 `connectedDevice` foreground service로 명시한다.
- Android 12+에서 `BLUETOOTH_SCAN`, `BLUETOOTH_CONNECT` 런타임 권한을 요청한다.
- 위치를 추론하지 않으므로 `neverForLocation`을 선언하고 위치 권한은 요청하지 않는다.
- 다만 Android 문서가 일부 BLE 비콘이 필터링될 수 있다고 경고하므로 실기기 시험에서
  반드시 확인한다.

### BP-006 — 큰 표면은 잠깐, 사용자가 허용한 때만 쓴다

- `SYSTEM_ALERT_WINDOW`는 큰 연결 카드에만 쓰고 별도의 상시 service나 광고 표면을 만들지 않는다.
- 전화·알람 전용 full-screen intent를 일반 연결 카드에 오용하지 않는다.
- 잠금화면과 화면 꺼짐에서는 overlay를 생략한다. 방해 금지 중에도 화면을 보고 있고 잠금이
  풀렸다면 무음 overlay를 허용한다. 이 정정의 실측 근거는 설계 009에 남긴다.
- 권한이 없으면 기능 전체가 실패하지 않고 기존 notification을 fallback으로 유지한다.
- overlay가 service보다 오래 남지 않도록 disconnect/destroy에서도 명시적으로 제거한다.

## 4. 베스트 프랙티스 반복 검증

### 검증 1 — 사용자 시나리오와의 대조

- 위젯을 후속으로 미루면 S-002가 성립하지 않는다. 따라서 위젯은 1차 필수다.
- 상시 대기 알림을 사용하면 광고 대신 다른 방해가 남는다. 연결 세션 범위로 줄인다.
- `0%` 기본값은 권한 거부와 실제 방전을 구분하지 못한다. nullable 상태 계약이 필요하다.

### 검증 2 — Android 공식 제약과의 대조

- Android 공식 Bluetooth 권한 문서는 스캔과 페어링 기기 통신을 각각
  `BLUETOOTH_SCAN`, `BLUETOOTH_CONNECT`로 구분한다.
- 위치 비사용 선언은 가능하지만 일부 비콘 필터링 가능성이 있어 실기기 검증이 필요하다.
- 위젯은 `RemoteViews` 제약을 가지므로 복잡한 실시간 UI보다 명확한 텍스트·아이콘과
  클릭 새로고침이 적합하다.

### 검증 3 — 공개 구현 세 가지와의 대조

- CAPod는 좌·우·케이스 배터리, 충전 상태, 팝업, 위젯이 실제 제품 범위가 될 수 있음을
  보여 준다.
- Podsify는 Apple company ID `0x004C`, proximity header `07 19`, 배터리 nibble과
  충전 flag 해석을 Apache-2.0 코드에서 독립적으로 확인시켜 준다.
- GreenPods도 같은 공개 패킷 구조와 10% 간격을 사용하지만 좌우 배치가 다른 구현과
  반대다. 이 충돌 때문에 실기기 한쪽 충전 시험을 생략할 수 없다.

### 검증 4 — 현재 기기 상태와의 대조

- SM-F971N에는 AirPods Pro가 하나만 페어링되어 있다.
- Android Bluetooth dump에는 A2DP, AVRCP, Handsfree 연결 능력은 있지만 연결 해제
  상태에서 좌·우·케이스 배터리는 노출되지 않았다.
- 따라서 표준 Bluetooth 상태만 조회하는 위젯으로는 요구를 충족할 수 없고 BLE
  manufacturer data 관찰이 기반이 되어야 한다.

## 5. 범위 밖

- ANC/주변음 원격 전환
- 착용 감지 기반 자동 재생·정지
- 공간 음향과 머리 추적
- Apple 펌웨어 업데이트 및 나의 찾기
- 다른 기기의 자동 연결·강제 해제
- 광고, 계정, 클라우드 동기화, 사용 분석

이 기능들은 중요하지 않아서가 아니라, 배터리 앱의 정확성과 수명주기를 검증하기 전에
비공개 AAP 제어까지 넣으면 실패 원인을 분리할 수 없기 때문에 제외한다.

## 6. 설계하면서 든 생각과 느낌

MaterialPods의 광고가 싫어서 새 앱을 만드는데, 우리가 상시 대기 알림과 권한 요청을
잔뜩 남기면 문제의 겉모습만 바꾸는 셈이라는 불편함이 먼저 들었다. 반대로 배터리를
“잘 보여 주는” 화면에 집중하다 보면, 미수신 값을 예쁜 0%나 오래된 현재값으로 꾸미기
쉽다는 긴장도 남는다.

그래서 이번 설계에서 가장 마음이 가는 부분은 화려한 AirPods 그림이 아니라 `—`,
`마지막 확인`, `연결 안 됨` 같은 문구다. 이 앱의 신뢰는 숫자를 많이 보여 주는 데서가
아니라 언제 그 숫자를 믿으면 안 되는지도 같은 크기로 말하는 데서 생긴다고 생각한다.
