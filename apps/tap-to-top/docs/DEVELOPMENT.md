# 맨 위로 톡 개발 안내

[사용법](../README.md) · [해결하려던 문제](../../../problems/tap-status-bar-to-scroll-top.md)

목표는 반복 입력으로 반드시 맨 위에 도착하는 것이 아니라, 상태 표시줄을 눌렀을 때 자연스럽게
위로 움직이고 손으로 언제든 멈출 수 있게 하는 것입니다. 아주 긴 피드는 여러 번 눌러야 할 수 있습니다.

## 선택한 방식과 버린 방식

iOS 앱의 `UIScrollView`는 자기 목록의 맨 위 위치를 알고 애니메이션할 수 있습니다.
Android 접근성 서비스가 다른 모든 앱에 같은 동작을 명령할 수 있는 공통 API는 없습니다.

- 위치 이동 명령은 일부 화면에서 애니메이션 없이 바로 도착했습니다.
- 여러 스와이프를 이어 보내면 감속 뒤 다시 가속하고, 사용자가 중간에 가로채도 다음 입력이 남았습니다.
- X의 홈 탭을 고정 좌표로 누르는 방식은 화면 상태에 따라 게시물을 누를 수 있어 사용하지 않습니다.

현재는 위쪽으로 한 번의 빠른 스와이프를 보내고 이후의 관성 이동은 대상 앱에 맡깁니다.
X에는 다른 이동값을 사용하지만, 앱 업데이트와 피드 구조에 따라 결과가 달라집니다.
이 한계를 숨기려고 반복 입력이나 불확실한 좌표 클릭을 다시 추가하지 않습니다.

## 구조

소스는 [`src/com/chocho/taptotop/`](../src/com/chocho/taptotop/)에 있습니다.

- 탭 판단: `TapTrigger`. 한 번·두 번 탭과 드래그를 구분합니다.
- 이동값: `ScrollOptions`. 범위를 제한하고 잘못된 저장값에는 기본값을 적용합니다.
- 저장: `AppSettings`. 일시정지·값 초기화와 접근성 권한을 분리합니다.
- 시스템 연동: `TapToTopService`. 스크롤 영역 탐색과 제스처 실행을 담당하며 불필요한 연속 입력을 보내지 않습니다.
- 설정 화면: `MainActivity`, `SettingsUi`. 공통 편집기의 저장·취소 규칙을 사용합니다.

스크롤 세기는 60–160%, 입력 길이는 40–75%입니다. 길이는 손가락 입력의 화면 비율이지 목록의 이동 거리가 아닙니다.
상태 표시줄을 아래로 끄는 동작은 알림창에 전달되어야 합니다. 화면 크기·회전·Fold 상태가 바뀌면
터치 영역도 다시 확인합니다. 화면 구조와 사용 기록을 저장하거나 전송하지 않습니다.

## 검사하기

저장소 루트에서 실행합니다. [공통 빌드 준비](../../../docs/GETTING-STARTED.md)가 필요합니다.

```sh
sh shared/android-ui/test-core.sh
sh apps/tap-to-top/test-core.sh
sh apps/tap-to-top/build.sh
```

모델 검사는 탭 시간·이동 경계와 옵션을 검사합니다. 실제 제스처 전달이나 앱의 관성 스크롤을 대신하지 않습니다.
실기기에서는 X·YouTube·Chrome·Samsung 설정에서 각각 짧은 목록과 긴 목록을 시험합니다.
한 번 이동한 뒤 추가 가속이 없는지, 중간에 손으로 멈추거나 반대로 움직일 수 있는지,
알림창 드래그가 유지되는지 확인합니다. 커버 화면·펼친 화면은 별도 결과로 남깁니다.

[기존 확인 범위](../../../compatibility/README.md) 밖의 기기에서는 지원을 단정하지 않습니다.
새 옵션을 넣을 때는 탭·스크롤 모델 → 서비스 연결 → 설정 화면 순으로 검증합니다.
