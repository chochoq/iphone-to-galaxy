# D-004: 결과 예측·시험·피드백 루프

## 1. 구현 전 예측 형식

각 변경은 코드를 쓰기 전에 아래를 채운다.

```text
가설:
바뀌는 사용자 관찰:
바뀌지 않아야 할 관찰:
가장 가능성 높은 실패:
실패가 뜻하는 설계 수정:
```

"부드러워질 것"처럼 반증할 수 없는 표현은 쓰지 않는다. 시작/끝 시간, 재가속
횟수, 최종 위치, 입력 후 남은 자동 이동처럼 화면에서 셀 수 있는 값으로 바꾼다.

## 2. 공통 시험 방법

### 기능

- 상태 표시줄 단일 탭 5회.
- 상태 표시줄 아래 드래그 5회.
- 이미 맨 위에서 탭 3회.
- 중간·깊은 위치에서 각각 탭.
- 세로/가로 및 폴드 접힘/펼침.

### 애니메이션

- 가능한 최대 fps로 화면을 녹화한다.
- 탭 직전 마지막 정지 프레임, 첫 이동 프레임, 마지막 이동 프레임을 표시한다.
- 연속 프레임의 콘텐츠 위치 변화량을 비교해 2차 가속이 있는지 본다.
- 영상 편집 컷이나 동적 콘텐츠 로딩은 속도 근거에서 제외한다.

### 사용자 가로채기

- 이동 시작 직후/중간/끝 직전에 반대 드래그를 한다.
- 손을 뗀 뒤 앱이 다시 위로 가속하면 실패다.
- 자동 동작 예약이 0개인지 코드와 런타임 양쪽에서 확인한다.

### 실제 맨 위

- 최초 앱 진입 화면의 상단 표식을 기준 캡처한다.
- 실행 뒤 같은 표식과 스크롤 가능 방향을 비교한다.
- "많이 올라감"을 맨 위 성공으로 세지 않는다.

| X 홈 피드 | 최우선 목표, 플랫폼 한계 별도 표기 | 필수 | 필수 | 필수 |
| 스크롤 없는 화면 | 무동작 | 해당 없음 | 해당 없음 | 필수 |

## 4. 피드백 분류

| 관찰 | 먼저 의심할 층 | 설계 반영 |
|---|---|---|
| 엉뚱한 가로 목록이 움직임 | 후보 선택 | D-003 점수 수정 |
| X만 맨 위에 못 감 | 능력/앱별 전략 | R 기록 후 D-003 전략 재평가 |
| 빠름-느림-빠름 | 실행 수명 주기 | 예약/다중 발사 제거 |
| 사용자가 내려도 다시 올라감 | 취소/예약 | B 계층을 수정한 뒤 앱별 보정 재시험 |
| 탭이 알림창 드래그로 오인 | 입력 분류 | 임계값과 시간 조건 수정 |
| 위치 액션 true지만 무동작 | 앱의 잘못된 능력 보고 | 앱/노드 조건으로 semantic 전략 제외 |

## 5. 완료 조건

- 모든 구현 태스크가 연결된 설계 ID와 시험 증거를 가진다.
- 해결하지 못한 플랫폼 한계가 README와 결과 문서에 사실대로 적힌다.
- 기존 1.4.0보다 나빠진 앱이 하나라도 있으면 새 버전을 설치 완료로 간주하지 않는다.
- 임시 진단 자료에는 사용자 콘텐츠가 남을 수 있으므로 분석 뒤 삭제한다.
