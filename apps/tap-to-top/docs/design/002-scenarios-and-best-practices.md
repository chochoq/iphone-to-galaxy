# D-002: 사용자 시나리오와 베스트 프랙티스

## 1. 성공을 판단하는 공통 언어

- **실제 맨 위**: 첫 콘텐츠와 앱의 상단 UI가 평상시 최초 진입 상태와 같다.
- **단일 이동**: 프레임 속도 곡선에 두 번째 발사로 설명되는 재가속이 없다.
- **가로채기**: 이동 중 사용자가 반대 방향으로 드래그했을 때 200ms 이내에
  자동 이동이 더 이상 사용자의 손을 거스르지 않는다.
- **안전한 무동작**: 잘못된 화면을 움직이는 것보다 아무 일도 하지 않는 편이
  나은 상황에서 화면 상태를 보존한다.

## 2. S-001: 일반 목록에서 상태 표시줄 탭

### 시나리오

사용자는 설정·연락처·목록형 앱을 여러 화면 아래까지 읽었다. 상태 표시줄을 한 번
탭한다. 상단 앱 바 자체가 아니라 그 아래의 주 콘텐츠가 맨 위로 이동해야 한다.

### 베스트 프랙티스

1. 화면에서 보이는 애플리케이션 창만 후보로 삼는다.
2. 스크롤 가능 표시뿐 아니라 `SCROLL_TO_POSITION`, `SCROLL_UP`,
   `SCROLL_BACKWARD` 액션을 함께 본다.
3. 절대 위치 액션이 실제로 지원되면 row/column 0 요청을 먼저 시험한다.
4. 지원하지 않으면 단일 플릭 한 번만 보낸다.
5. 스크롤 후보가 모호하면 가장 넓다는 이유만으로 배너·수평 탭을 고르지 않는다.

### 반복 검증

- 1차: Samsung 설정의 긴 목록.
- 2차: Chrome의 긴 웹 문서.
- 3차: 접힘/펼침 상태 각각에서 동일 후보가 선택되는지 확인.

## 3. S-002: X의 매우 긴 홈 피드

### 시나리오

사용자는 X에서 여러 게시물을 내려 읽었다. 탭하면 화면 몇 장만 위로 갈 것이
아니라 가능하면 최신 첫 게시물까지 가길 원한다.

### 확인한 실패 이력

- 1.4.0의 한 번 플릭은 자연스럽지만 아주 긴 피드의 절대 맨 위를 보장하지 않는다.
- 선택된 하단 `홈` 탭 재선택 시험을 작은 contact sheet만 보고 처음에는
  무동작으로 잘못 판정했다. 폴더블의 꺼진 2448px 디스플레이가 기본 녹화되어
  실제 1248px 활성 화면이 좁게 보인 것이 원인이었다.
- 활성 디스플레이 ID를 지정한 원본 PTS를 다시 확인하자 X 자체 이동은 약
  0.90~1.28초 구간, 즉 약 0.38초 동안 프레임마다 이어졌다. 중간 재가속은 없었다.
- 이 기능을 서비스에서 호출하는 시제품을 만들자 더 강한 실패가 발견됐다. X는
  사용자가 아래로 읽을 때 하단 바를 시각적으로 숨기지만, 접근성 트리의 홈 노드는
  같은 bounds와 `isVisibleToUser == true` 상태로 남겼다. 숨겨진 좌표를 누르자
  피드 맨 위가 아니라 그 좌표 아래의 게시물 상세 화면이 열렸다.
- 반복 플릭은 더 멀리 가지만 빠름-느림-빠름과 입력 탈취를 만든다.

### 베스트 프랙티스

1. X는 접근성 트리에 절대 위치 액션을 노출하지 않으므로 그 경로를 사용할 수 없다.
2. 하단 홈 노드의 접근성 `visible` 값은 실제 렌더링 가시성 증거로 쓰지 않는다.
3. 보이지 않는 앱 UI 좌표를 추정해 누르지 않는다. 엉뚱한 게시물·좋아요·링크를
   여는 위험이 실제 맨 위 이득보다 크다.
4. 현재는 기존 단일 플릭 한 번을 유지한다. 깊은 피드에서 실제 맨 위를 보장하지
   못하는 한계를 README에 사실대로 적는다.
5. 두 번째 홈 탭이나 플릭을 예약해 재가속을 만들지 않는다.

## 4. S-003: Chrome/YouTube에서 사용자가 중간에 마음을 바꿈

### 시나리오

사용자가 상태 표시줄을 눌렀지만 올라가는 동안 방금 보던 내용을 다시 보고 싶어
화면을 아래 방향으로 드래그한다.

### 베스트 프랙티스

1. 미래 시점의 플릭이나 접근성 액션을 예약하지 않는다.
2. 단일 합성 제스처의 전달이 끝난 뒤 관성은 대상 앱이 소유하게 한다.
3. 터치 시작 이벤트를 받을 수 있다면 내부 실행 상태를 즉시 `IDLE`로 돌린다.
4. 중단 뒤 1초 동안 같은 자동 동작이 다시 발생하지 않는지 검사한다.

### 반복 검증

- Chrome: 시작 직후, 중간 감속 구간, 거의 끝난 구간의 세 시점에서 가로챈다.
- YouTube: 홈 피드와 검색 결과를 따로 시험한다.
- 시험은 프레임 녹화와 실제 손 조작을 함께 사용한다. ADB의 두 번째 합성 제스처만
  사용하면 실제 사용자 우선순위를 완전히 검증하지 못한다.

## 5. S-004: 상태 표시줄을 아래로 끌어 알림창 열기

### 시나리오

상태 표시줄을 짧게 탭하지 않고 아래로 드래그한다. 스크롤 이동은 없어야 하고
알림창만 열려야 한다.

### 베스트 프랙티스

- 수직 이동이 터치 오차 범위를 넘고 수평 이동보다 클 때 한 번만 알림창을 연다.
- 포인터가 110px 오버레이 밖으로 빠질 때 오는 `ACTION_CANCEL`도 마지막 raw 좌표로
  드래그를 판정한다. 가운데에서 시작하면 `MOVE`만으로 24dp를 넘기기 전에
  CANCEL되는 실기기 동작을 확인했다.
- `ACTION_UP`에서 맨 위 동작이 중복 실행되지 않게 drag 상태를 고정한다.
- 짧은 대각선 탭과 실제 드래그를 각각 5회 반복한다.

## 6. S-005: 이미 맨 위이거나 스크롤 화면이 아님

### 베스트 프랙티스

- 이미 맨 위라면 시각적 튐·새로고침·탭 전환을 만들지 않는다.
- 카메라·게임·전체 화면 동영상처럼 일반 스크롤이 없으면 안전하게 무동작한다.
- 상태 표시줄이 숨겨진 전체 화면에는 보이지 않는 터치 영역을 억지로 만들지 않는다.

## 7. S-006: 여러 스크롤 영역

### 시나리오

수평 탭 행, 댓글 목록, 본문 웹뷰처럼 스크롤 가능한 노드가 둘 이상 있다.

### 베스트 프랙티스

- 수직 주 콘텐츠, 화면 중심과의 겹침, 가시 면적, 지원 액션을 점수로 분리한다.
- `SCROLL_TO_POSITION` 지원 하나만으로 작은 수평 캐러셀을 주 대상으로 올리지 않는다.
- 후보와 선택 이유는 텍스트 없이 클래스·경계·액션 ID만 진단 로그에 남길 수 있다.
