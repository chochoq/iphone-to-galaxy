# D-003: Android 구조와 의존성

## 1. 플랫폼 간 구조 차이

```text
iPhone
상태 표시줄 탭
  -> UIKit이 대상 UIScrollView를 결정
  -> 앱 내부 스크롤 뷰가 실제 offset 0으로 한 번에 애니메이션

Android 개인용 접근성 앱
상태 표시줄 오버레이 탭
  -> 우리 서비스가 다른 앱의 접근성 트리에서 후보를 추정
  -> 앱이 노출한 의미 액션을 요청하거나 손가락 제스처를 합성
```

Android 쪽에는 다른 모든 앱의 스크롤 offset을 읽고 `animated scrollTo(0)`을
호출하는 공통 권한이 없다. 이 차이가 기능의 가장 강한 의존성이다.

## 2. 의존성이 강한 순서

문서의 설명 순서대로 개발하지 않는다. 다음 기반이 흔들리면 위에 얹은 앱별
튜닝이 전부 무효가 되므로 아래 순서로 구현한다.

### A. 기능 탐지와 후보 선택

먼저 실제 앱의 노드가 어떤 접근성 액션을 제공하는지 알아야 한다. 특히
`ACTION_SCROLL_TO_POSITION`을 지원하는지, row/column 0을 받는지, 그 결과가
부드러운지 확인한다. 여기서 실패하면 "정확한 맨 위"를 일반 기능으로 설계할 수
없다.

후보 점수는 다음 요소를 독립적으로 둔다.

- 애플리케이션 창인가
- 세로 크기와 가시 면적
- 화면 중심을 포함하는가
- 수직 스크롤 액션을 제공하는가
- 절대 위치 액션을 제공하는가
- 수평 탭/캐러셀처럼 높이가 지나치게 작지 않은가

### B. 실행 수명 주기와 취소

상태는 최소한 다음처럼 명시한다.

```text
IDLE -> RESOLVING -> REQUESTED -> IDLE
             \-> NO_TARGET -> IDLE
사용자 새 터치/서비스 중단/창 전환 -> IDLE
```

미래 제스처를 예약하지 않는 것이 가장 강한 취소 보장이다. 의미 액션이 앱 내부
애니메이션을 시작한 뒤의 중단 가능성은 앱 구현에 달려 있으므로 앱별 시험 결과를
기록한다.

### C. 전략 선택기

전략 우선순위:

1. `SINGLE_NATIVE_FLING`: 화면 안에서 아래 방향 플릭 한 번. 앱의 일반 관성에 맡김.
2. `NO_OP`: 안전한 대상이 없을 때.

향후 앱이 실제 의미 기반 맨 위 액션을 안전하게 노출하면
`APP_OWNED_NATIVE_TOP`을 이보다 앞에 추가할 수 있지만 현재 검증 통과 앱은 없다.

현재 기각 전략:

- `REPEATED_FLING`: 재가속과 사용자 입력 탈취 때문에 기각.
- 애니메이션 없는 `SEMANTIC_ABSOLUTE_TOP`: Samsung 설정에서는 실제 상단으로
  갔지만 즉시 점프하여 사용자가 요청한 경험과 반대라 기각.
- `X_HOME_RESELECT`: 실제 하단 바가 보일 때는 앱 소유 이동을 만들었지만, 바가
  숨은 상태를 접근성 트리로 구별할 수 없어 같은 좌표의 게시물을 여는 회귀 때문에
  기각.
- 무제한 `SCROLL_BACKWARD` 루프: 정확한 상단은 얻을 수 있어도 단절된 페이지
  이동과 늦은 자동 실행이 생기므로 기각.

### D. 앱별 보정

앱별 보정은 A~C가 완성된 뒤 마지막에 둔다. 패키지 이름만 보고 동작을 바꾸면
화면 종류가 다른 같은 앱에서 오작동하기 쉽다. 보정이 필요하면 패키지뿐 아니라
노드 능력·화면 구조·실패 결과를 함께 조건으로 쓴다.

## 3. 의미 액션 실험 규약

`ACTION_SCROLL_TO_POSITION`은 지원 표시만 믿지 않는다.

1. 대상의 액션 목록을 텍스트 없이 기록한다.
2. `ACTION_ARGUMENT_ROW_INT = 0`, `ACTION_ARGUMENT_COLUMN_INT = 0`을 전달한다.
3. `performAction` 반환값을 기록한다.
4. 반환값이 true여도 실제 화면이 맨 위인지 별도로 본다.
5. 이동이 즉시 점프인지 연속 애니메이션인지 프레임으로 분류한다.
6. 잘못된 노드가 움직이면 후보 점수 설계를 먼저 고친다.

Samsung 설정의 실험은 true를 반환하고 실제 상단으로 갔지만 녹화에 중간 이동
프레임이 하나도 없어 즉시 점프로 판정했다. 따라서 현재 제품 경로에는 넣지 않는다.

실패했을 때 같은 탭 안에서 바로 플릭을 이어 보내면 이중 이동처럼 보일 수 있다.
따라서 첫 버전에서는 액션 반환이 false일 때만 단일 플릭으로 폴백하고, true인데
무동작하는 앱은 검증 결과를 바탕으로 명시적으로 제외한다.

## 4. 입력 영역 설계

- 높이는 실제 상태 표시줄 높이에 맞춘다.
- 탭 허용 이동은 14dp, 알림창 드래그 판단은 24dp를 시작값으로 유지한다.
- 오버레이는 포커스를 갖지 않고 상태 표시줄 이외의 앱 터치를 가로채지 않는다.
- 화면 회전·폴드 전환·서비스 재연결 때 현재 디스플레이 치수로 다시 설치한다.

## 5. 개인정보와 진단

기능 탐지를 위해 노드의 클래스·bounds·액션 ID·패키지만 필요하다. 화면 텍스트,
content description, 계정명은 로그에 남기지 않는다. 인터넷 권한은 계속 두지
않는다. 릴리스 빌드에는 상세 진단 로그를 끄거나 최소화한다.

## 6. 내 생각과 위험 감각

이 기능은 겉으로는 탭 하나라 작아 보이지만, 사실은 "다른 앱 안의 어느 스크롤을
어떤 의미로 움직일 것인가"라는 플랫폼 경계 문제다. 나는 여기서 앱별 속도 숫자를
먼저 만지는 것이 가장 위험하다고 본다. X의 45ms를 35ms로 바꾸면 테스트 한 번은
좋아질 수 있지만 구조적 한계는 그대로이고 다른 화면을 더 거칠게 만든다.

반대로 기능 탐지와 취소를 먼저 굳히면, 나중에 Android나 X가 새로운 접근성 액션을
노출해도 전략 하나만 교체할 수 있다. 실제로 이번 검증에서 표준 위치 액션은
정확하지만 딱딱했고, X의 앱 소유 동작은 보이는 UI 좌표에만 안전했다. 사용자가
말한 "의존성이 강한 것부터"가 이 작업에서는 바로 이 경계 추상화다.
