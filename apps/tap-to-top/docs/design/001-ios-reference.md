# D-001: iPhone 기준 동작

## 1. 확인하려는 질문

사용자가 말한 "스르르르르륵"을 단지 느린 스와이프라고 번역하면 안 된다.
확인할 것은 다음 네 가지다.

1. 상태 표시줄을 탭했을 때 누가 스크롤을 시작하는가?
2. 하나의 이동인가, 여러 번의 플릭인가?
3. 항상 같은 시간과 속도 곡선인가?
4. 언제 동작하지 않으며, 이동 중 사용자 입력은 어떻게 취급되는가?

## 2. Apple 공식 문서로 확정된 계약

근거:

- [UIScrollView.scrollsToTop](https://developer.apple.com/documentation/uikit/uiscrollview/scrollstotop)
- [scrollViewShouldScrollToTop](https://developer.apple.com/documentation/uikit/uiscrollviewdelegate/scrollviewshouldscrolltotop(_:))
- [scrollViewDidScrollToTop](https://developer.apple.com/documentation/uikit/uiscrollviewdelegate/scrollviewdidscrolltotop(_:))

확정된 사실은 다음과 같다.

- 상태 표시줄 탭은 손가락 스와이프를 재생하는 기능이 아니다.
- 시스템은 상태 표시줄과 가장 가까운 `UIScrollView`에 맨 위로 스크롤할지를
  묻고, 허용된 그 스크롤 뷰가 자기 콘텐츠 오프셋을 맨 위로 옮긴다.
- `scrollsToTop`이 꺼져 있거나 delegate가 거절하거나 이미 맨 위이면 아무 일도
  일어나지 않는다.
- 완료 뒤 `scrollViewDidScrollToTop`이 호출된다.
- iPhone 화면에 `scrollsToTop == true`인 스크롤 뷰가 둘 이상이면 동작하지 않을
  수 있다.

이 계약에서 중요한 제품 해석은 "시스템 전체가 동일한 플릭을 주입한다"가
아니라 "각 앱 내부의 스크롤 컴포넌트가 의미 기반 요청을 처리한다"는 점이다.

## 3. 공개 화면 녹화로 관찰한 모양

### 검증 A: Safari 장문 페이지

- 공개 영상 `5-3Eg7JUwIM`의 장문 Safari 구간을 25fps 프레임으로 비교했다.
- 해당 예에서는 약 0.8~0.9초 동안 한 번의 연속 이동으로 보였다.
- 중간에 속도가 다시 커지는 두 번째 발사는 보이지 않았다.

### 검증 B: Safari/Wikipedia 별도 영상

- 공개 영상 `4sFr6LJZ-Oc`를 29.97fps 원본으로 다시 받았다.
- 탭 직전 정지 구간 뒤 약 11.6초 지점부터 프레임마다 다른 위치가 이어지고,
  약 12.1초 무렵 상단에 도달했다. 대략 0.5초인 한 사례다.
- 여기에서도 빠름-느림-다시 빠름 형태의 재가속은 보이지 않았다.

### 검증 C: 소셜 앱 영상

- Instagram/X 공개 시연도 확인했으나 편집 컷·동적 이미지 로딩·낮은 촬영 품질이
  섞여 있어 정밀한 시간 자료로 쓰지 않는다.
- "탭 뒤 앱의 실제 상단으로 간다"는 기능 확인에만 보조 자료로 쓴다.

### 관찰에서 확정할 수 있는 것과 없는 것

확정 가능한 공통점:

- 한 번의 네이티브 이동이다.
- 반복 발사에 의한 속도 리셋이 보이지 않는다.
- 최종 목적지는 해당 스크롤 뷰의 실제 맨 위다.

확정하면 안 되는 것:

- `0.5초` 또는 `0.8초`를 고정 iPhone 규격이라고 부르는 것.
- 공개 영상 하나의 감속 곡선을 모든 iOS 버전·앱에 일반화하는 것.
- 편집된 영상으로 사용자 터치 중단 동작을 추정하는 것.

## 4. 아직 공개 사양으로 확인되지 않은 부분

Apple 공식 문서는 상태 표시줄 탭 애니메이션의 정확한 duration과 easing 함수를
공개하지 않는다. 공개 영상의 시간이 서로 다르므로 거리·OS·앱 구현이 영향을
줄 수 있다고 취급하되, 이것도 내부 구현 사실로 단정하지 않는다.

이동 도중 새 손가락 터치가 상태 표시줄 맨 위 애니메이션을 어떤 프레임에서
중단하는지도 위 공식 문서에는 없다. 일반 `UIScrollView`의 직접 조작 우선 원칙과
제품 경험은 참고할 수 있지만, 별도 실기기 촬영 전까지 이 항목의 증거 상태는
`미확정`이다.

## 5. 설계 결론과 내 판단

내가 보기에 사용자가 어색하다고 느낀 핵심은 속도 숫자가 아니라 "한 의도가
여러 번 다시 시작되는 것"이다. 그래서 Android에서 800ms짜리 스와이프를 만드는
것보다, 가능한 경우 앱이 가진 절대-맨위 의미 동작을 호출하고 그럴 수 없을 때
딱 한 번의 관성만 만드는 편이 훨씬 정직하고 iPhone답다.

정확히 복제할 수 없는 부분을 감추려고 반복 플릭을 더 촘촘히 배치하면 잠깐은
맨 위에 더 잘 도달해 보여도 Chrome/YouTube의 사용자 가로채기를 다시 망가뜨린다.
이 트레이드오프는 구현 편의보다 사용자 제어권을 우선한다.
