# T-001: 실행 태스크와 판단 이력

이 문서는 할 일 제목의 모음이 아니다. 나중에 다른 사람이 제목만 보고 "무엇을
어떻게 확인해야 하는지" 재현하지 못한다면 태스크가 과도하게 요약된 것이다.

## 1. iPhone 기준을 관찰과 사양으로 분리한다

### 1.1 공식 계약을 고정한다

#### 1.1.1 Apple의 `scrollsToTop` 문서를 원문 기준으로 읽고 트리거·대상 선택·무동작 조건·완료 콜백을 각각 기록한다 — 완료

처음에는 "상단을 누르면 부드럽게 올라간다"를 하나의 기능처럼 다뤘다. 그러나
이 문장만으로는 Android에서 스와이프를 흉내 내야 하는지 앱의 의미 액션을 찾아야
하는지 결정할 수 없다. 공식 문서 세 개를 분리해 읽은 결과, iOS는 상태 표시줄
탭을 가장 가까운 UIScrollView에 전달하고 그 뷰가 허용 여부와 완료를 소유한다는
구조가 확인되었다. 결과는 D-001 §2에 기록했다.

#### 1.1.2 Apple이 공개하지 않은 duration/easing을 공식 사실처럼 쓰지 않도록 미확정 목록을 만든다 — 완료

이전 관찰의 약 0.8초를 고정값으로 만들 위험이 있었다. 별도 영상에서는 약 0.5초
사례가 나왔고 Apple 문서에는 숫자가 없다. 따라서 시간 숫자는 개별 관찰값으로만
남기고 제품 상수의 근거로 쓰지 않는다.

### 1.2 화면 녹화로 단일 이동인지 반복 검증한다

#### 1.2.1 서로 다른 Safari 공개 영상 두 개를 원본 fps로 내려받아 첫 이동부터 마지막 이동까지 프레임을 배열한다 — 완료

두 영상 모두 반복 플릭에서 보였던 중간 재가속은 없었다. 시간은 서로 달라 정확한
곡선 복제 자료가 아니라 "한 번의 연속 이동"을 판별하는 자료로만 채택했다.

#### 1.2.2 소셜 앱 영상은 편집·로딩 여부를 확인하고 시간 근거에서 제외할지 판정한다 — 완료

Instagram 시연은 0.1초 사이에 빈 플레이스홀더와 전혀 다른 이미지가 섞여 편집
또는 로딩 영향이 컸다. 기능 존재의 보조 증거만 유지한다.

#### 1.2.3 iPhone 실제 기기에서 이동 중 손가락 가로채기를 3개 시점에 촬영한다 — 대기

공식 문서와 공개 시연이 이 상황을 직접 보여 주지 않는다. iPhone 실기기 또는
편집되지 않은 해당 시험 영상을 확보하기 전에는 성공/실패를 추론하지 않는다.

## 2. Android의 의미 기반 절대-맨위 능력을 먼저 검증한다

### 2.1 진단이 사용자 콘텐츠를 수집하지 않게 만든다

#### 2.1.1 선택 후보의 패키지·클래스·bounds·액션 ID만 출력하고 text/contentDescription은 출력하지 않는 진단 경로를 구현한다 — 완료

현재 `uiautomator dump`는 사용자 피드 텍스트까지 포함하므로 반복 진단 도구로
부적절하다. 서비스 내부에서 필요한 메타데이터만 ADB logcat에 남기는 짧은 경로를
만들었다. 실제 로그에 화면 텍스트와 contentDescription이 없음을 확인했다. 최종
릴리스 전에 상세 로그 상수를 끄는 태스크를 5.2.3에 포함한다.

#### 2.1.2 X·Chrome·YouTube·Samsung 설정에서 후보와 `ACTION_SCROLL_TO_POSITION` 지원을 수집한다 — 완료

각 앱을 중간 스크롤 위치로 옮기고 같은 진단 경로를 통과시켰다. Samsung 설정의
`androidx.recyclerview.widget.RecyclerView`만 액션 ID 16908343을 제공했다.
X의 Compose View, Chrome WebView, YouTube ScrollView/RecyclerView는 제공하지
않았다. 상세 bounds와 액션 목록은 R-001 §5에 남겼다.

### 2.2 위치 0 액션의 실제 의미를 검증한다

#### 2.2.1 row/column 0 bundle로 `performAction`을 호출하고 반환값·최종 위치·프레임 형태를 함께 기록한다 — 완료, 제품 전략 기각

Samsung 설정에서 true를 반환했고 실제 첫 설정 항목으로 갔다. 그러나 화면
녹화의 직전/직후 사이에 중간 위치 프레임이 없어 즉시 점프로 판정했다. 정확한
상단 하나만 보고 채택했다면 사용자가 처음 지적한 어색함을 되살릴 뻔했다.

#### 2.2.2 true지만 무동작·즉시 점프·잘못된 영역이 움직이는 앱을 semantic 제외표에 남긴다 — 완료

Samsung 설정 RecyclerView는 `즉시 점프`로 제외했다. X·Chrome·YouTube는 액션
미지원이다. 앱 버전과 후보 클래스/경계는 R-001에 남겼다.

## 3. 실행 수명 주기와 사용자 우선권을 고정한다

### 3.1 자동 동작이 한 번만 존재하도록 만든다

#### 3.1.1 상태 표시줄 탭 한 번에 의미 액션 하나 또는 합성 제스처 하나만 생성됨을 코드 구조와 로그로 증명한다 — 완료

최종 1.4.1에는 semantic과 앱 UI 좌표 탭이 없고 `dispatchGesture` 호출도 단일
플릭 한 곳뿐이다. `handler.post`와 `postDelayed`가 없음을 검색으로 확인했다.

#### 3.1.2 서비스 interrupt·창 전환·사용자 터치 시작에서 남은 callback이 0개인지 검사한다 — 완료

예약 작업 자체가 없고 interrupt·destroy·overlay cancel에서 handler를 비운다.
Chrome과 YouTube에서 상태 탭 0.25초 뒤 반대 드래그를 넣었을 때 선택한 위치에
멈췄으며 이후 다시 올라가는 프레임이 없었다.

### 3.2 상태 표시줄을 벗어나는 드래그를 보존한다

#### 3.2.1 오버레이 밖으로 내려가며 발생한 ACTION_CANCEL의 마지막 좌표로 알림창 드래그를 판정한다 — 완료

실기기 ADB 드래그를 `(300,70) -> (300,850)`으로 보냈을 때 서비스는 y=130까지
MOVE를 받은 뒤 y=137에서 CANCEL을 받았다. 시작점 기준 24dp는 약 63px라 MOVE
구간에서는 임계값을 넘지 못했고 기존 CANCEL 분기가 아무 동작 없이 종료했다.
CANCEL 시점의 67px 하향 이동은 임계값을 넘으므로 이때 알림창을 한 번 열고,
`dragHandled`로 탭 동작과 중복되지 않게 구현했다. 동일한 `(300,70)` 시작 드래그로
알림창 전체가 열린 것을 캡처로 확인하고 다시 접었다.

## 4. 후보 선택과 전략을 구현한다

### 4.1 후보 선택기를 능력 중심으로 분리한다

#### 4.1.1 작은 수평 스크롤과 전체 높이 수직 콘텐츠를 구별하는 점수 항목을 코드에 이름 있는 함수로 분리한다 — 대기, 2.1 자료 의존

현재는 면적에 절대 위치 지원이면 10억 점을 더한다. 이 방식은 작은 캐러셀이
위치 액션을 가진 경우 잘못 선택할 수 있다. 실측 bounds와 액션 목록이 생긴 뒤
가중치를 정한다.

### 4.2 전략 우선순위를 구현한다

#### 4.2.1 X 홈 피드에 `APP_OWNED_NATIVE_TOP`을 적용할 수 있는지 구현하고 숨은 내비게이션까지 검증한다 — 완료, 전략 기각

선택된 하단 홈 노드와 조상을 확인하는 시제품은 홈 노드를 찾아 탭 요청까지
성공했다. 하지만 깊게 스크롤해 하단 바가 시각적으로 숨은 상태에서도 X가 같은
노드를 visible로 보고했고, 실제 좌표에는 피드 게시물이 있어 상세 화면을 열었다.
구현을 폐기하고 `SINGLE_NATIVE_FLING`만 남긴다. 이는 "능력 있음"과 "안전하게
호출 가능"이 다른 문제라는 이력을 보존한다.

#### 4.2.2 X의 45ms 상수를 능력 검증 결과와 함께 재평가한다 — 완료, 유지

더 빠르게 만드는 것이 무조건 개선이라는 가정을 버렸다. 45ms는 이미 단일 플릭의
높은 초기 속도이고 더 짧게 해도 Android/X의 최대 관성 거리 한계를 없애지 못한다.
추가 속도 변경 근거가 없어 기준선을 유지한다.

## 5. 결과를 예측하고 실기기 회귀 시험한다

### 5.1 구현 전에 앱별 예상표를 쓴다

#### 5.1.1 각 앱에서 선택될 전략·예상 종착점·예상 중단 동작·가장 가능성 높은 실패를 R 문서에 먼저 기록한다 — 완료

### 5.2 실제 결과를 예상과 비교한다

#### 5.2.1 Samsung 설정·Chrome·YouTube·X에서 기능/단일 이동/가로채기/알림창 행렬을 채운다 — 완료, 실제 손 검증 1건 남음

ADB 합성 반대 드래그로 Chrome과 YouTube의 가로채기는 통과했다. 실제 손가락
검증은 사용자가 다음 사용 때 체감 확인할 항목으로 남겼다. X는 피드 화면을
유지했고, 아주 긴 피드의 절대 상단은 플랫폼 한계로 실패 상태를 숨기지 않는다.

#### 5.2.2 예상과 다른 결과마다 원인을 후보 선택·능력 보고·실행 수명·앱 한계 중 하나로 분류하고 D 문서를 먼저 수정한다 — 완료

두 차례의 판정 수정과 알림 CANCEL 문제를 R과 D에 먼저 반영한 뒤 최종 코드를
복구·수정했다.

#### 5.2.3 임시 공개 영상과 사용자 화면 캡처를 삭제하고 APK 권한·서명·설치 버전을 확인한다 — 완료

이번 조사에서 만든 `/tmp/taptotop-iphone-recheck`의 영상·프레임·XML을 모두 삭제했다.
기기에 만든 시험 녹화도 매 시험 직후 삭제했다. 최종 APK는 일반 요청 권한 없음,
v3 서명 signer 1개, 설치본 1.4.1/versionCode 6, 접근성 서비스 활성 상태를
확인했다. APK SHA-256은
`4e8f7811ffba13e42a55b76623d53e57eacdbea5cc58214a6521d1b87a5bb2a1`이다.
